## Implementation Integrity Verdict

**Pass.** The interface is a coherent system, not an interchangeable template:

- Colour, type, spacing, radii and motion come from `css/tokens.css`; components and views consume tokens rather than one-off values. The detector found **no raw-colour findings**.
- Theme, language and direction are cached before the first paint (`index.html` inline bootstrap), then reconciled with `/api/state`; system-theme changes are listened for (`app.js`).
- Light, dark, `prefers-contrast: more` and `forced-colors: active` variants are explicitly handled. The forced-colors pass produced `Canvas`/`CanvasText`, removed shadows and kept the borders.
- Controls are built through `components/ui.js` (real `button`, `role="switch"`, `aria-pressed`, `aria-checked`), not clickable divs.
- The seven detector advisories are deliberate parts of the Ember identity, not drift: four spring easings (the motion signature), compact titlebar padding (Windows chrome), the skeleton shimmer (loading placeholder) and the Ember glow (the identity element). They remain advisories, not defects.
- No fake content, no lorem, no placeholder product copy; the fixture data is confined to the harness.

**Limitation:** the live FoxyVPN instance (pid 4312) has no remote-debugging port and was not relaunched, because it is carrying a live tunnel. The detector therefore ran against the source, and the rendered checks ran against the same `web/` assets in Chromium 1243. A WebView2/CDP pixel scan, native DPI behaviour, Narrator/NVDA and real touch were not exercised. This is disclosed wherever it affects a conclusion.

## Detailed Findings by Severity

### [P2] Route changes leave focus in the navigation rail and are not announced

- **Location:** `js/app.js:171–212` (`go`), `js/app.js:214–228` (`navigate` + `hashchange`); nav items `js/app.js:140–155`; view headings `views/home.js:95`, `views/locations.js:38`, `views/logs.js:24`, `views/settings.js:17`.
- **Category:** Accessibility
- **Evidence:** With Locations focused, pressing Enter changed the hash to `#/locations` but left `document.activeElement` on `BUTTON.nav-item.is-active` (“Locations”). Tab then went Settings → Logs → `#accountBtn` → `#locSearch`: four stops before the new view’s first control. Pressing Ctrl+1 while typing in `#locSearch` changed the view to `#/home` and dropped focus to `BODY`; no live region announced the view.
- **Impact:** Keyboard-only users must traverse the rest of the rail on every view change. Screen-reader users get no confirmation that the view changed; `aria-current` updates silently and the `<title>` change is not reliably announced.
- **Standard:** WCAG 2.4.3 focus order is not violated (the order is still logical), but this is the standard SPA focus-management gap; 4.1.3 status messages applies to status, not context changes, so it is a P2 rather than a P1.
- **Recommendation:** After a user-initiated `go()`, focus the visible view’s `h1` with `tabindex="-1"` and `.focus({ preventScroll: true })`, or call `announce(t('nav.' + name))` (and keep the `aria-current` update). Skip this on first paint. The h1s already exist on every signed-in view.
- **Suggested command:** `/impeccable harden`

### [P2] The signed-out screen has no programmatic heading

- **Location:** `views/home.js:191–197` (sign-in intro); `.signin-lede` styling in `css/views.css:201`; the only home `h1` is created in the signed-in stage at `views/home.js:95`.
- **Category:** Accessibility
- **Evidence:** In `signed-out`, `document.querySelectorAll('h1')` returned `[]` and `h1,h2,h3,h4,h5,h6` returned `[]`. `<main>` contains `.signin-intro` with `p.signin-lede` (“Free 50 GB a month…”) and `p.signin-note`. Focus order starts with the window buttons, then “Sign in with Firefox”, “Create an account”, and the language buttons.
- **Impact:** A screen-reader user entering the app lands in an unnamed main region with no heading to navigate by; heading navigation skips the entire first-run screen. The visual hierarchy is clear, so this is a semantics gap rather than a visual one.
- **Standard:** WCAG 1.3.1 (info and relationships) best practice; a page with no heading is not automatically an AA failure, hence P2.
- **Recommendation:** Add an `h1` with a new `signin.title` key (“Sign in to FoxyVPN” / Persian equivalent), visually hidden if the layout must not change, or promote the lede to `h1` and reset its weight. Keep exactly one `h1`.
- **Suggested command:** `/impeccable harden`

### [P2] Two different “Details” controls in the failure state

- **Location:** Banner summary `js/components/overlay.js:290–295`; stage primary action `views/home.js:265–266`; shared key `error.details` at `js/i18n.js:277` (English) and `:572` (Persian).
- **Category:** Accessibility / labelling
- **Evidence:** The error state’s focus order contains `summary:Details` and `button#primaryAction:Details`. The summary expands the raw error text; the button navigates to `#/logs`. The stage action is correctly the quiet secondary button; the banner correctly owns retry. Only the name collides.
- **Impact:** Screen-reader and voice-control users hear or say “Details” twice with different outcomes; “click Details” is ambiguous. Visual users can disambiguate by position, so the workaround exists.
- **Standard:** WCAG 2.4.6 / 2.4.4 are not violated (each visible label matches its name), but 2.5.3 and voice-control disambiguation are compromised.
- **Recommendation:** Rename the banner summary to “Error details” with a new `error.detailsSummary` key (Persian “جزئیات خطا”) and keep the stage “Details”; this preserves the approved failure hierarchy. The alternative is renaming the stage action to “View logs”.
- **Suggested command:** `/impeccable clarify` or `/impeccable harden`

### [P3] Ctrl+1–4 navigate while typing in an editable field

- **Location:** `js/app.js:1030–1037` (global keydown handler); no editable-target guard.
- **Category:** Accessibility / keyboard
- **Evidence:** With `#locSearch` focused and “amst” typed, Ctrl+1 changed the hash to `#/home` and left focus on `BODY`; the field and the query disappeared with the view.
- **Impact:** Unexpected context change and loss of typed input for keyboard users; conflicts with common browser/OS tab shortcuts. Because the shortcut uses Ctrl, WCAG 2.1.4 (character key shortcuts) does not apply, so this is P3.
- **Recommendation:** Ignore Ctrl+1–4 when `e.target.closest('input, textarea, select, [contenteditable="true"]')` matches. Keep Ctrl+F focusing the app search. If global jumps must work while editing, require Ctrl+Alt.
- **Suggested command:** `/impeccable harden`

### [P3] `will-change` left on at rest and a persistent sticky blur

- **Location:** `css/views.css:301–313` — `will-change: transform, opacity` sat in the shared ambient group (`.ambient::before`, `.ambient::after`, `.ambient .mesh`, `.ambient .ambient-warn`, `.ambient .ambient-danger`), so it applied to every ambient layer at rest. The home DOM creates only `.ambient > .mesh`; the warn/danger classes are dormant selectors. Sticky blurred header at `css/views.css:798–804` (`.loc-group-title { position: sticky; backdrop-filter: blur(6px); }`).
- **Category:** Performance
- **Impact:** A permanent, broad compositor hint on the ambient layers and a blurred sticky surface can cost layer memory and repaints on low-end GPUs. No frame drop was measured in this audit; the rest of the app is lean.
- **Recommendation:** Move `will-change` to `.stage[data-state="error"] .ambient-danger` or drop it (the opacity transition is cheap). Keep the sticky blur but verify on the lowest supported GPU, or switch to a solid `color-mix` background at compact sizes. No visual change.
- **Suggested command:** `/impeccable optimize`

### [P3] Touch targets below 44×44 (desktop density)

- **Location:** `.tb-btn` 32×24 (`css/base.css:221–226`); `.switch` 44×24 (`css/components.css:100`); `.icon-btn` 32×32, `.sm` 28×28, `.lg` 36×36 (`css/components.css:79–96`); buttons 36/44 high.
- **Category:** Responsive
- **Evidence:** Across twelve runs there were **0 controls below 24×24** — WCAG 2.2 SC 2.5.8 (AA) passes. The 44×44 heuristic fails for the titlebar controls, switch and icon buttons.
- **Impact:** On a Windows tablet/touchscreen, the 24px-high caption controls and switch are small; mouse users are fine. The product is a pointer-first Windows client, not a mobile app.
- **Recommendation:** Accept as deliberate Windows density, or enlarge hit areas without changing visuals (transparent padding/`::before` to 44×44) for the titlebar and switch if touch is in scope. Verify at 200% Windows scaling.
- **Suggested command:** `/impeccable adapt` (optional)

### [P3] Setting descriptions are not programmatically associated with their controls

- **Location:** `views/settings.js:36–51` builds `.setting-label` and `.setting-desc`; `switchControl` call sites (e.g. `views/settings.js:104`) never pass `describedBy`; `components/ui.js` already supports `aria-describedby`.
- **Category:** Accessibility
- **Impact:** A screen-reader user hears “Verify exit IP, switch, on” but not the explanation unless they navigate to the adjacent text separately. The visual relationship is lost.
- **Standard:** WCAG 1.3.1 relationship best practice; the control does have a name, so this is P3.
- **Recommendation:** Give each `.setting-desc` an id and pass it to `switchControl({ describedBy })`; do the same for segmented controls or inputs that have an explanatory description. Mechanical, no visual change.
- **Suggested command:** `/impeccable harden`

## Patterns & Systemic Issues

- **Dynamic-context accessibility is the weak axis.** Controls themselves are well labelled and keyboard-operable; the gap is at the *route/view* level: focus is not moved or announced when the view changes, and the signed-out view never gets a heading. One centralized `afterNavigate` hook (focus/announce) would fix the class, not just one view.
- **Shared i18n keys can collide across surfaces.** `error.details` is used by both the banner disclosure and the stage action. A short label-collision sweep (same key, different action) would catch similar cases.
- **Performance hints are broad, not scoped.** `will-change` is left on a hidden ambient layer and `backdrop-filter` sits on a persistent sticky header. Both are minor on desktop, but the pattern is “hint once, never remove”. Scope hints to the active state.
- **Desktop density is deliberate** (24–36px controls, 760px native minimum). The 44px touch heuristic is not met by design; if touch becomes a target, a systematic hit-area pass is needed rather than per-component tweaks.

## Positive Findings

- **Contrast:** 0 failures across dark, light, English, Persian and error states. Lowest measured text pair: **4.85:1** (`span.loc-sub`, FA Locations), then **4.94:1** (`#accountSub`, light) and **5.17:1** (dark). Placeholders pass. The focus ring deliberately pairs a light ring with a dark halo so it survives the accent fill (`base.css:60–77`).
- **Accessible names:** 0 unnamed controls across twelve runs. Real buttons throughout; switches expose `role="switch"` + `aria-checked`; navigation exposes `aria-current="page"`; the account button exposes `aria-expanded`; the failure banner is `role="alert"`; the log view is `role="log"`; toast and live-status regions are polite.
- **Keyboard:** every one of the 16 sampled tab stops showed a visible `:focus-visible` ring, including the `<summary>` and inputs. The Accounts modal has `aria-modal="true"`, traps Tab (ten stops stayed inside), closes on Escape, restores focus to `#accountBtn`, and resets `aria-expanded` to `false`.
- **Semantics:** one `h1` per signed-in view; `nav`, `main` and `aside` landmarks; labelled titlebar window buttons; no clickable divs in the control set.
- **Motion:** `prefers-reduced-motion: reduce` collapses animation/transition durations to 1e-06 s; final states remain visible, so hierarchy and state are preserved. No flashing. The blunt global kill is acceptable for an Operate surface (P3 note only).
- **Forced colors / high contrast:** explicit `@media (forced-colors: active)` and `@media (prefers-contrast: more)` blocks; emulation produced `Canvas`/`CanvasText`, visible borders and no shadows.
- **Responsive:** home, settings, locations, logs, signed-out and error all pass at **760×560** with no horizontal overflow (`html`/`body` scrollWidth == clientWidth). The short-height home keeps the primary action in view; the Persian locations/logs views stay RTL, and the log transcript stays LTR.
- **Theming:** full token system; theme and language are cached pre-paint; system-theme changes are live; no raw surface colours; no theme flash.
- **Implementation:** vanilla modules, no dependencies, no images to lazy-load, no layout-thrashing loops. The detector returned **7 advisories and 0 violations**, all sanctioned by `DESIGN.md`.

## Method & Limitations

**What was exercised**

- Fixture harness at `http://127.0.0.1:4173` serving the real `web/` tree unmodified; state seeded by scenario.
- Chromium 1243 (Playwright), 1× DPR, 1000×700 and 760×560.
- Twelve runs: connected dark, connected light, connected 760, error-timeout, signed-out, settings, locations (FA), logs (FA, 760), plus settings/locations/signed-out/error at 760.
- DOM/computed-style checks: accessible names, roles, headings, landmarks, target boxes, horizontal overflow.
- Contrast: composited effective backgrounds from computed colours (walking ancestors), all text nodes ≥11px, placeholders via `::placeholder`.
- Keyboard: 16 tab stops per view, focus-visible outline/shadow, modal trap/Escape/return, 760 keyboard navigation, Ctrl+1 in a text field.
- Motion/contrast/forced colors: Playwright media emulation, computed durations and system colours.
- Detector: source scan (`impeccable detect --json foxy-windows/web`), 7 advisories, 0 raw-colour.
- Edge probe: 380×280, 500×400, 600×450 (≈200% browser zoom of the 760 native minimum) for overflow and stack/primary visibility.

**What was not exercised**

- The **live WebView2 app** (pid 4312) had no CDP port and was not relaunched; the tunnel stayed up. This means no WebView2-specific pixel/DPI check and no native chrome interaction. The same assets were audited in Chromium.
- **Narrator/NVDA** screen-reader output; **real touch** gestures; **native Windows 200% text scaling** (Windows DPI is the supported path; the app uses px tokens).
- **Runtime frame timing** (no trace); performance conclusions are code-level plus detector.
- The **OAuth/code-entry modal** and the **About** modal were not opened in this audit. The Accounts modal exercised the shared overlay primitive; the About modal was verified in the earlier onboard pass.
- The 380px probe is outside the native 760px floor: it had no horizontal overflow, but the side stack was dropped and the primary action sat below the 280px viewport. Treat it as “below the supported floor”, not as a supported layout.

**Ratings rationale**

- A11y **3/4**: AA essentials pass; the P2 route-focus/sign-in-heading gaps and the label collision are meaningful for AT users.
- Performance **3/4**: lean and fast; the two P3 hints are the only improvements.
- Theming **4/4**: complete and verified across all four theme modes.
- Responsive **3/4**: every supported size passes; 44px touch density and zoom-below-floor are the caveats.
- Integrity **4/4**: coherent system; sanctioned advisories; no drift. The live CDP scan limitation is disclosed above.
