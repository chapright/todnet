## What Was Fixed

### P2 — Route focus and announcement — **Fixed**

- **Changes:** `js/app.js:171–176` adds `focusView()`; `go()` accepts `{ focus }` and focuses the new view’s `h1` after its update (`:178–218`); `navigate()` and `hashchange` request focus (`:224–238`); sign-out (`:281–284`) focuses the sign-in heading. The h1 receives `tabindex="-1"` and `.focus({ preventScroll: true })`.
- **Focus ring:** `css/base.css` suppresses the control ring on a programmatically focused view heading (`h1[tabindex="-1"]`), because a heading is a reading target, not a control.
- **Verified:** From Home, focusing Locations and pressing Enter leaves `document.activeElement` on `H1.view-title` “Locations”, inside `<main>`. The next Tab goes straight to `#locSearch`, not to Settings/Logs/Accounts. After Ctrl+1 while typing in `#locSearch`, the hash stays `#/locations`, focus stays in the input, and the value “amst” survives.
- **Standard:** WCAG 2.4.3 focus order preserved; the SPA context-change gap is closed. Screen readers announce the focused h1.

### P2 — Sign-in screen heading — **Fixed**

- **Changes:** `views/home.js:193–196` adds `h('h1', { class: 'sr-only', text: t('signin.title') })` as the first child of `.signin-intro`. `js/i18n.js` adds `signin.title` in both locales (“Sign in to FoxyVPN” / “ورود به FoxyVPN”).
- **Verified:** The signed-out DOM now has exactly one heading: `H1 “Sign in to FoxyVPN”`. The `sr-only` heading adds no visual change.
- **Standard:** WCAG 1.3.1 structure; heading navigation now names the first-run screen.

### P2 — Duplicate “Details” — **Fixed**

- **Changes:** `components/overlay.js:292` now uses `t('error.detailsSummary')`; both locales add `error.detailsSummary` (“Error details” / “جزئیات خطا”). The stage action keeps `error.details` (“Details”).
- **Verified:** In the error state, the banner disclosure is “Error details”; `#primaryAction` is “Details”; the focus order confirms the two names no longer collide. `role="alert"` and the retry actions are unchanged.

### P3 — Shortcut guard — **Fixed**

- **Changes:** `js/app.js:1030–1049` detects an editable target (`input`, `textarea`, `select`, `contenteditable`) and returns before the Ctrl+1–4 branch. Ctrl+F still drives the app’s search.
- **Verified:** Ctrl+1 in `#locSearch` no longer navigates; Ctrl+4 from the body still goes to Logs and focuses its h1.

### P3 — Setting descriptions — **Fixed**

- **Changes:** `views/settings.js` gives each `.setting-desc` a unique id and sets `aria-describedby` on the row’s control when it does not already have one.
- **Verified:** Twelve setting rows now resolve a description: Transport, Tunnel mode, Verify exit IP, Connect on launch, Direct fallback, System proxy, Launch at startup, Start minimized, Theme, SOCKS5 port, HTTP proxy port, Verbose logs. The two rows without a description (“Language”, the account row) are unaffected.
- **Standard:** WCAG 1.3.1 relationship; the visible explanation is now programmatically tied to the switch/group/input.

### P3 — `will-change` at rest — **Fixed (with a correction)**

- **Correction to the pre-fix report:** the `will-change` line was not on a single `.ambient-danger` element. It sat in the shared ambient group at `css/views.css:301–313` (`.ambient::before`, `.ambient::after`, `.ambient .mesh`, `.ambient .ambient-warn`, `.ambient .ambient-danger`). The actual home DOM creates only `.ambient > .mesh`; the warn/danger classes are dormant selectors. The property was therefore a broad hint on every ambient layer at rest, not a targeted one.
- **Change:** removed `will-change: transform, opacity` from the shared group. No replacement rule was added, because the error-state `.ambient-danger` node does not exist; adding one would be dead code.
- **Verified:** `document.querySelector('.ambient-danger')` returns `null` in the rendered home state (the node is absent), so no computed style applies. The rendered ambient layers (`.ambient::before`, `::after`, `.mesh`) no longer carry a permanent hint; the opacity transitions still run. The drift rules for the dormant warn/danger classes are untouched and unused.
- **Remaining:** the sticky `.loc-group-title` still uses `backdrop-filter: blur(6px)` (`css/views.css:798–804`). This is the only reason Performance remains 3. It is a small sticky header, and no frame drop was measured; it is safe to leave or verify on the lowest supported GPU.

## Remaining Issues

### [P3] Sticky locations-group backdrop blur

- **Location:** `css/views.css:798–804` (`.loc-group-title { position: sticky; backdrop-filter: blur(6px); }`).
- **Impact:** a blurred sticky surface can repaint on scroll on a low-end GPU. No frame drop was measured; contrast at the sticky header is 5.83:1.
- **Recommendation:** leave as-is after a quick low-end check, or use a solid `color-mix` background at compact sizes. No visual change needed.
- **Command:** `/impeccable optimize` (optional).

### [P3] Touch targets below 44×44 (desktop density)

- **Location:** `.tb-btn` 32×24; `.switch` 44×24; `.icon-btn` 28–36; buttons 36/44.
- **Impact:** all controls meet the 24×24 WCAG 2.5.8 minimum; on a Windows tablet, the 24px-high titlebar/switch are small. The product is pointer-first Windows 10/11, not mobile.
- **Recommendation:** accept as deliberate density, or enlarge hit areas invisibly (padding/`::before`) if touch is formally in scope.
- **Command:** `/impeccable adapt` (optional).

### Note — 200% browser zoom

At an effective 380 CSS px (200% zoom of the 760px native floor) there is no horizontal overflow, but the side stack is dropped and the primary action falls below the 280px viewport. This is outside the supported window floor; Windows DPI scaling is the supported resize path. If WebView2’s Ctrl+Plus is enabled and 200% zoom is in scope, pin the zoom or add a reflow check. Not counted as a finding.
